# M8 Stage 2 인과 결과

## 실행 조건

- **실행 방식:** 전체 영상을 인과적으로 rollout했다(출력 → 다음 crop 중심 → 다음 frame).
- **기준선:** 같은 기계의 SGGL과 비교했다.
  - RunPod RTX 4090 arm은 `runpod/runs/SGGL`과 짝짓는다.
  - Ubuntu RTX 2080 arm은 diag 궤적과 짝짓는다.
- **판정 대상:** 작은 객체(prompt 면적 < 1%) 57단위 / 34영상이다.
- **통계:** 영상 군집 bootstrap 2000회. 판정 규칙은 사전 등록(`preregistration.json` `stage2_causal_rule`)을 따른다.
- **원자료:** `outputs/milestone8/causal_report.json`, `causal_per_unit.csv`
- **재생성:** `uv run python scripts/m8_analysis.py causal`

**사전 등록과 다른 점:**
- Stage 1에서 진출 조건을 통과한 생성기 계열이 없었다.
- 그래서 Stage 1 재생에서 순 이득이 양수였던 유일한 조합(F_oclr8_L + score>0)과, 그와 짝을 이루는 foveation을 '진단적 인과 실행'으로 돌렸다.
- 운동 계열 대조(FLOWVEL, M3vel)는 16:14 KST에 고정했다.
  - 정정: 이 시점은 M8 사전 등록(`preregistration.json`) 이후이고, Stage 1 diag 7단위가 이미 기록된 뒤다.
  - 인과 출력이 나오기 전에 고정한 것은 맞다(첫 인과 출력 18:41).

## 2. 핵심 발견

1. **후보 생성보다 crop 제어가 이겼다.**
   - FLOWVEL(+0.0130)은 순위화도, SAM 2 추가 호출도 없이 '완벽한 순위화와 존재 판정을 갖춘 rescue'의 상한(ORACLE_POOL +0.0136)과 같은 크기의 이득을 냈다.
   - 이유: FLOWVEL은 놓친 frame을 사후에 찾지 않는다. 같은 기계 기준으로 GT가 있는 동시 부재 frame을 **131 → 63**으로 줄였다. 놓칠 일 자체를 줄인 것이다. M3vel은 108이었다.
2. **배포 가능한 rescue(출력만 바꾸는 것)는 효과가 없다.**
   - RESC_OCLR은 11 frame을 회수했지만 거짓 재획득이 6 늘었다. 회수한 다음 frame에서 다시 놓치는 경우가 많았다.
3. **메모리 기록은 장기 효과를 만들지만 위험도 키운다.**
   - RESC_OCLR_ADMIT은 RESC_OCLR 대비 +0.0047이었다.
   - 그러나 잘못된 rescue가 메모리에 들어가 miami-surf obj4에서 −0.116의 신원 전환이 났다.
   - 이것은 DAM4SAM, SENTRY 등 '검증 후 기록' 계열이 노리는 문제와 같다.
4. **foveation은 해롭다.** 주변이 더 넓게 보이면서 방해물 거짓 양성이 늘었다(거짓 재획득 118 vs 93). disc-jockey obj3에서 −0.330 신원 전환이 났다.
5. **M3vel은 두 기계(Vast, RunPod)에서 같은 값으로 재현됐다**(+0.0046). 그러나 이득 영상이 2개뿐이라 여전히 INCONCLUSIVE다.

## 2.1 FLOWVEL ablation: 효과의 원천은 '부재 중 crop 운반'이다

| 변형 | 출력이 있을 때 | 두 view 모두 부재일 때 | ΔJ&F | 놓친 동시 부재 frame (GT 있음, SGGL 131) |
|---|---|---|---|---|
| FLOWVEL | 출력 중심 + 0.5 × 대상 광류 | 광류 box 중심 + 0.5 × 대상 광류 | +0.0130 | 63 |
| FV_PRESENT | 출력 중심 + 0.5 × 대상 광류 | **고정 (SGGL과 같음)** | +0.0016 | 110 |
| FLOWCARRY | 출력 중심 (SGGL과 같음) | 대상 영역 광류로 운반한 box 중심 | **+0.0141** | 62 |
| CAMCARRY | 출력 중심 (SGGL과 같음) | 이전 중심 + **카메라 전역 운동** (대상 주변 바깥의 median flow) | +0.0137 | 63 |

**짝 비교 (같은 단위, 영상 군집 CI, `pairwise_report.json`):**

| 비교 | Δ | 95% CI |
|---|---|---|
| FLOWCARRY − FLOWVEL | +0.0011 | [−0.0000, +0.0024] |
| CAMCARRY − FLOWVEL | +0.0007 | [−0.0001, +0.0017] |
| FLOWCARRY − CAMCARRY | +0.0003 | [−0.0001, +0.0012] |
| FLOWVEL − FV_PRESENT | **+0.0114** | [+0.0000, +0.0259] |
| FLOWVEL − M3vel | +0.0084 | [−0.0012, +0.0239] |

**결론 (독립 검토 후 정정):**
- 이득의 거의 전부가 '두 view가 대상을 놓친 동안 crop을 움직이는 것'에서 온다.
  - 속도만 쓰는 FV_PRESENT는 기여하지 않는다.
  - 다만 FLOWVEL − FV_PRESENT의 CI 하한은 0에 붙어 있고, bootstrap seed에 따라 부호가 바뀐다.
- **FLOWCARRY ≈ CAMCARRY는 구성상 당연하다.**
  - 대상을 놓친 동안 운반 box는 이미 대상 위에 있지 않다. 그래서 그 box 안의 광류는 대부분 배경 흐름이다.
  - 따라서 이 비교로 '대상 광류 vs 카메라 운동'을 분리할 수 없다.
- **해석:**
  - SGGL은 출력이 비면 crop을 영상 좌표에 그대로 둔다(`set_center(None)`).
  - 장면이 움직이는 동안 대상은 crop 밖으로 나간다. 부재 중 crop을 장면 움직임에 맞춰 옮기면 대상이 crop 안에 남는다.
  - '카메라 운동 보정'은 이와 일치하는 **가설**이다. 카메라 운동 자체(`trk.cam`)는 기록하지 않았다.
- **비용:** 세 형태 모두 지금 구현은 frame마다 전체 frame RAFT가 필요하다. 지연은 SGGL 대비 약 +14%다(RunPod 동시 실행 측정).
- **사후 선택:** FLOWCARRY와 CAMCARRY는 FLOWVEL 결과를 본 뒤 ablation으로 고정했다. 그래서 대표 결과는 출력 전에 고정한 FLOWVEL로 보고한다.

## 5. 기계 간 재현 (FLOWVEL_U, Ubuntu RTX 2080)

- **성격:** 같은 코드와 같은 데이터를 다른 GPU에서 다시 계산한 **계산 재현**이다. 효과의 독립 재현이 아니다.
- **설정:** FLOWVEL과 동일하다. 20:50 KST에 출력 전 고정했다. Ubuntu diag SGGL과 짝지을 수 있는 작은 객체 46단위에서 비교했다.
- **결과:** +0.0161 [+0.0014, +0.0345]. 상승 영상 5개 / 하락 1개, 최악 단위 −0.023.
- **RunPod FLOWVEL과의 단위별 일치:** 상관 0.999998, 최대 차이 0.0008. GPU 차이로 결과가 바뀌지 않는다는 뜻이다.
- 나머지 11단위는 RunPod에서만 diag를 실행해 Ubuntu 기준선이 없으므로 제외했다.
